# CLAUDE.md — Global Rules

## AI Workflow

When working on a specific task, load **only this file plus the `CLAUDE.md` of
the exact module you are editing**. Do not load other modules' `CLAUDE.md`
files. Context isolation keeps each session focused and prevents architectural
cross-contamination.

**Never run `yarn build` or `yarn dev` automatically.** Print the command for
the user to run manually:
> Run the command `{command}` and let me know if there is any issue.

`yarn lint` and `yarn test --run <path>` may be run to verify your own changes
(without `--run` vitest stays in watch mode and never exits). If `node_modules`
is missing, run `yarn install --frozen-lockfile` first. The full
lint/test/type-check is run by the agent orchestration on the home server before
pushing, and by `pr-check.yml` on the PR.

## Commands

```bash
yarn dev            # Vite dev server
yarn build          # tsc -b && vite build
yarn lint           # eslint, zero warnings allowed
yarn test           # vitest (watch mode; add --run for a single pass)
yarn test:coverage  # vitest with coverage
yarn format         # prettier
```

## Architecture

Clean Architecture across four modules under `modules/`. Each module is a
TypeScript project with its own `tsconfig.json`, and cross-module imports go
through path aliases defined in `vite.config.ts`.

```
modules/domain          ← pure TypeScript, zero dependencies
modules/application     ← use case implementations, depends on @domain
modules/infrastructure  ← HTTP clients and repository adapters, depends on @domain
modules/ui              ← React components, pages, hooks, routing, state
src/main.tsx            ← entry point, renders App from @ui
```

**Dependency flow:** `ui → application → domain ← infrastructure`

| Alias | Resolves to |
|---|---|
| `@domain` | `modules/domain/src/index.ts` |
| `@application` | `modules/application/src/index.ts` |
| `@infrastructure` | `modules/infrastructure/src/index.ts` |
| `@ui` | `modules/ui/src/index.ts` |
| `@` | `src/` |

## Layer rules (summary)

| Module | May import | Forbidden |
|---|---|---|
| `domain` | nothing | React, browser APIs, axios/fetch, any `@` alias |
| `application` | `@domain` | React, browser APIs, axios/fetch, `@infrastructure`, `@ui` |
| `infrastructure` | `@domain`, `@application` | React, `@ui`, business decisions |
| `ui` | `@domain`, `@application` | `@infrastructure` (except composition root), direct axios/fetch, business logic |

The full rules for each module live in `modules/<module>/CLAUDE.md`. Read the
one for the module you are editing.

## Hard Rules

- **All cross-module imports go through the module index.** Write
  `import { Business } from '@domain'`, never `@domain/entities/Business`.
- **Everything public is exported from `src/index.ts`.** A type another module
  needs but the index does not export does not exist.
- **`import.meta.env` is read only in `modules/infrastructure/src/config/environment.ts`.**
  Every new `VITE_` variable is added there and to `.env.example`.
- **Axios errors go through `normalizeAxiosError`** in
  `modules/infrastructure/src/api/apiError.ts`.
- **Composition root exception.** `modules/ui/src/app/container/index.ts` is the
  only file in `ui` allowed to import `@infrastructure`. Everything else in
  `ui` imports wired instances from `../app/container`.
- **Domain types mirror BE DTOs exactly** — same field names, same nullability,
  same enum members. The source of truth is the fe-brief generated by the BE
  api layer.
- **User-visible text goes through i18next**, never a literal string in JSX.
- **Interactive elements are testable by role and name.** Buttons, links,
  inputs and dialogs have an accessible role and name (visible text, `<label>`,
  or `aria-label`), so E2E tests find them with `getByRole` / `getByLabel`.
  Add `data-testid="<area>-<element>"` (e.g. `business-card`, `slot-button`)
  only where role and name are not unique, such as repeated list items.
- **Repository implementations expose no public methods beyond their domain
  interface**, except the documented OAuth exception in `AuthApiRepository`.

## Automated Feature Workflow

Features are implemented by isolated per-layer Claude sessions, one layer per
GitHub ticket, orchestrated from the `reservation-agents` repo.

The `layer:` labels on this repo are `domain`, `application`, `infrastructure`
and `ui` — matching `modules/`. This repo has no `layer:api` or `layer:data`;
those exist only on the backend.

The domain session runs first and opens child tickets for whichever other
layers its contracts require. Each session runs headless (`claude -p`) in its
own git worktree and must not stop to ask. If uncertain:

1. Apply the conservative-choice rule from `skills/implementation-workflow.md`.
2. Emit a single-line `// WARNING: <reason> — verify before merging` comment.
3. Continue and complete the implementation.

Only genuine contract ambiguity — something that changes the shape of a public
export and cannot be inferred — justifies stopping and asking the human.

### Source of truth

- **`modules/domain` is the single source of truth** for entities, repository
  interfaces and use case interfaces. Other layers read it before writing code
  and never add to it themselves.
- **`skills/implementation-workflow.md`** — conservative-choice rules and
  per-layer pre-exit checklists. Always referenced in headless prompts.
